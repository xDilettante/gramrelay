# Durable updates and consumers (J2)

The tg-agent update journal shares the existing bounded database worker, WAL/FULL settings and private storage contract. Migrate reviewed schema v1/v2 to v3 transactionally without changing operation rows, hashes, fences, tombstones, updates or poll checkpoints. Verify the reviewed old schema before migration and the complete new schema before committing. Unsupported/foreign versions remain rejected.

JournalOptions.max_update_consumers bounds the total number of durable consumer IDs (256 by default, at most 1,000,000). Released consumers retain their positions and count toward this quota. A new consumer starts at the current retention floor; an existing consumer never silently skips a gap. Lease and acknowledgement tokens bind the issuing database instance as well as the feed, consumer and generation. They are private in-process proofs, not serializable grants.

A feed permanently binds one host profile to one numeric bot identity; aliases for the same bot in one database and rebinding a profile are rejected. The host verifies identity before starting a managed network collector. Feed policy is immutable across openings: retention (7 days by default), per-event bytes (1 MiB), batch/read bytes (1 MiB). Journal-wide defaults bound 64 feeds, 100,000 retained updates and 64 MiB of payloads. Limit overflow/configuration errors fail before acceptance. Capacity never evicts unexpired events.

Updates are serialized through the real generated DTOs, validated for a nonnegative ID and at most one known event, canonically encoded and fingerprinted. A live (profile, update_id) duplicate with the same fingerprint is idempotent; different content is Conflict. Preserve unknown event fields. Chat metadata is only an ordering hint, never an authorization grant. Debug/errors omit bodies, chat IDs, profile/cursor values and private paths. Incoming bodies may contain private data and are retained only according to host policy. A1 must check current scopes before reading/disclosing them.

Each feed has a strictly increasing local sequence independent of Telegram update_id and of other profiles. Opaque versioned cursors bind profile and sequence, are bounded/validated and are not access grants. read returns a bounded batch and next cursor. A cursor below the retention floor is CursorExpired; above the feed's high-water mark or for a different feed is rejected. A fresh read without a cursor starts at the current retained floor. Expiry removes a prefix and advances that floor; it never resets sequence numbers or consumer checkpoints. Deduplication of inbound updates lasts within this explicit retention window. Unlike operation keys, expired update rows can be deleted. Late delivery beyond that window has no deduplication guarantee; outbound operation journals remain independent.

Source leases exclude polling and webhook ownership across instances/processes using the same database. Claims/renew/release verify the worker and monotonically advancing source revision; time is sampled after acquiring the write transaction. An expired lease cannot renew or write. Normal database close releases only its own source leases. A process-local SDK guard also coordinates managed in-memory and durable collectors. Raw getUpdates/direct external consumers still require caller coordination.

Webhook append acknowledges only a committed transaction; R4 authenticates and bounds HTTP before calling it. Poll append atomically stores the entire ordered batch and its next offset. The next getUpdates offset always comes from this committed checkpoint, never from handler completion or a merely received response. Offset gaps are valid; negative/overflow/unsorted batches fail before commit. Empty polls do not advance the checkpoint or extend its freshness indefinitely. After 24 hours without a committed nonempty poll, request no offset to handle long idle/randomized identifiers conservatively. Mode changes invalidate an old polling offset. Private checkpoint tokens prevent overlapping/stale commits from advancing state. No network call is retried using an uncommitted offset.

Durable consumers have independent host-chosen IDs, versioned worker leases and committed local cursors. Reading does not acknowledge. Only the batch's opaque acknowledgement token may advance its consumer, after successful handlers. Concurrent consumers with different IDs are independent; two workers cannot own the same consumer concurrently. Expired consumer work is recoverable for at-least-once handling. Handler errors/panics/timeouts leave its cursor unchanged. Admission order within chats and a barrier for unknown scopes reuse the SDK dispatcher. External handler side effects are not exactly-once; use stable operation IDs and the operation journal. Retention expiry stops a lagging consumer explicitly; skipping an expired prefix requires an explicit host operation.

The managed polling collector validates bot identity, refuses an active webhook without deleting it, takes both source guards, renews within a bounded request budget and commits intake before requesting another offset. Cancellation stops intake and releases ownership; cancelled DB futures may still commit, so cleanup drains/queries the same journal. Controlled retries/backoff may repeat only the same already-durable acknowledgement offset. Runtime consumers drain bounded work on shutdown and persist only successful batch acknowledgements. R4 adds the HTTP adapter; A1 read_updates reads this local broker and never starts another poller.

Acceptance: v1/v2 migration preserves operations and update positions; schema/identity/policy mismatch fail closed; duplicate/conflicting/unknown updates; global row/byte/feed/consumer caps; whole-batch rollback; cursor binding/future/expiry; TTL/reclaimed capacity; independent process ownership and stale lease fencing; atomic checkpoint crash boundaries; no premature remote ack; independent consumer recovery/ack tokens; ordered dispatch/failure/shutdown; actual restart tests and offline examples. J2 storage, sources, consumers and managed polling are integrated and verified; HTTP authentication remains R4 and authorized tool access A1.

The tg-agent `bot` feature enables managed runtimes; storage alone does not enable the SDK bot layer. Intake defaults: batch 100, Telegram poll timeout 20 seconds, total request budget 30 seconds, empty delay 250 ms; request budget must fit at most half the source lease and exceed the poll timeout. There are no implicit RPC retries; restarting reloads the committed checkpoint. Consumer defaults reuse DispatchOptions (16 chat groups, 30-second handler timeout), batch 100, idle delay 250 ms, shutdown timeout 30 seconds. Lease refresh after reading and a lifetime margin precede handler admission. An independently polled heartbeat bounds renewal by the known expiry; a blocked renewal cancels handlers before ownership can expire under cooperative scheduling. Release and confirmation wait behind admitted DB jobs instead of failing on their own cancelled job's capacity permit. Shutdown bounds handlers; database draining/release remains an awaited separate cleanup step. Dropping an entire runtime future leaves a bounded lease to expire; callers should cancel its token and await it before closing the journal.
