# MCP для Telegram

MCP использует тот же `ToolSession`, исполнитель, разрешения, квоты и журнал,
что Rust API и CLI. Восемь имён и их JSON Schema совпадают с `tg-agent tools`.
Транспорт — локальный stdio через официальный `rmcp 3.10.0`; HTTP-сервер не
запускается. Поддержаны текущий протокол 2026-07-28 и прежний initialize-handshake.

С опцией `mtproto` встраиваемый хост может явно вызвать
`ToolSession::new(bot, principal).with_mtproto(mt_executor)`. Тогда `tools/list`
содержит расширенный каталог из 16 инструментов, совпадающий с
`tg-agent tools --mtproto`: прежние восемь и восемь `mtproto_*`. Версия каталога
равна 2; отдельные Request/ToolResponse остаются версии 1. Ошибки MT-записей
сохраняют ключ и направляют к `mtproto_get_operation`; потерянный ответ не
разрешает повтор. Сессии без провайдера продолжают объявлять восемь Bot tools.
Самостоятельная загрузка MTProto-профилей через `Host::load` использует
[конфигурацию v2](AGENT-MTPROTO.md); пример ниже показывает Bot-конфигурацию.
Встраиваемый хост после
завершения MCP закрывает MT Executor, Client и Journal в таком порядке.

## Запуск

```powershell
cargo build --locked -p tg-agent --features mcp --bin tg-agent
./target/debug/tg-agent.exe mcp --config C:/protected/host.json
```

Создайте защищённую конфигурацию по [руководству CLI](AGENT-CLI.md). Токен
поступает из указанной в профиле переменной окружения; не помещайте его в
аргументы инструментов или командную строку. MCP-клиент запускает бинарный файл
с аргументами `mcp`, `--config`, абсолютный путь. Переменные окружения передаёт
доверенный процесс запуска. Для проверки без RPC добавьте `--dry-run`.

`stdout` содержит только JSON-RPC. Ошибки запуска дают статический код в stderr
и exit 2, без JSON CLI в протокольном потоке. Обычный EOF закрывает журнал и
завершает процесс с exit 0; сбой транспорта/закрытия — exit 2. EOF отменяет
незавершённые вызовы. Завершение процесса операционной системой не гарантирует
доставку уже выполненного действия или ответа клиенту.

## Вызов и восстановление

В MCP `arguments` передаётся полный Request версии 1, как в CLI. Например,
параметры `tools/call` для записи:

```json
{
  "name": "send_message",
  "arguments": {
    "schema_version": 1,
    "profile": "demo",
    "operation_id": "task-42-message-1",
    "call": {
      "tool": "send_message",
      "arguments": {"chat_id": "123456", "text": "Готово"}
    }
  }
}
```

Отдельное имя MCP привязывается к `call.tool` до допуска. Подмена имени,
principal, token, URL, path, grant или approval не выдаёт полномочий. Для файлов
используйте предварительно зарегистрированный `file_handle`; callback должен
быть ранее наблюдён из разрешённого события. Подтверждения создаёт только хост
для точного запроса. См. ограничения callback и восстановления файлов в CLI.

`structuredContent` содержит общий `{schema_version,ok,result|dry_run|error}`;
один text-блок содержит тот же JSON. `isError` отражает ошибку интерфейса.
Квитанция операции, включая Unknown/Rejected, остаётся результатом: `ok=true`
не означает успешную отправку. Проверяйте `operation.state` и
`result_availability`. После отмены/тайм-аута/потери ответа вызывайте
`get_operation` с исходным ключом; новая попытка с новым ключом может повторить
эффект. До окончания аренды журнал может показывать `in_flight`; затем
незавершённая попытка становится `unknown`. Автоматического повтора Unknown нет.
Значения `telegram_json` и текст Telegram — недоверенные данные.

## Ограничения

- Одна строка JSON-RPC, включая LF: 128 KiB. Дубли декодированных JSON-ключей
  и превышение лимита закрывают соединение до передачи кадра SDK. Обычный
  разбор синтаксиса и протокола выполняет SDK.
- Нормализованный объект `arguments`: 64 KiB через общий Request parser. Пробелы
  внешнего JSON входят в предел кадра; CLI считает исходные байты документа.
- До 32 ожидающих ответов, включая очередь перед медленным stdout. Отменённый
  ID сохраняет слот до переподключения: старый ответ SDK не может завершить новый
  запрос с этим ID. После серии из 32 отмен переподключитесь.
- Ответ инструмента по умолчанию ограничен 8 MiB до создания text и structured
  представлений. Встроенный хост может выбрать `OutputLimit` от 1 KiB до 64 MiB.
  Размер всего MCP-кадра больше из-за двух представлений JSON и экранирования.
- Ожидание записи/flush ограничено пятью секундами без прогресса; обычный ответ
  также имеет абсолютный предел отправки пять секунд. Это охватывает ответы
  самого SDK об ошибках протокола. Потеря вывода не запускает Telegram повторно.

Каталог фиксирован и не зависит от текста Telegram. Аннотации — подсказки
клиенту; разрешения проверяет исполнитель. Сервер не объявляет tasks, resources,
prompts или изменяемый каталог. При встраивании настройте фильтр журналирования
SDK: уровни trace/debug `rmcp` могут содержать аргументы и результаты. Сам
исполняемый файл не устанавливает выводящий их subscriber.

## Проверка без Telegram

```powershell
cargo test --locked -p tg-agent --features mcp --test mcp_protocol --test mcp_stdio
cargo build --locked --offline -p tg-agent --features mcp --example mcp_fixture
python tools/mcp_fixture_check.py target/debug/examples/mcp_fixture.exe
```

Пример `mcp_fixture` — самостоятельный MCP-процесс с локальным mock Bot API,
временным журналом, тремя чатами и 18 фиксированными событиями. Профиль `archive`
разрешает только чтение. Десять независимых заданий и ответы находятся в
[questions.xml](../tg-agent/evals/v1/questions.xml); каждый запуск создаёт
исходное состояние заново. Набор проверяет поиск решения среди черновиков,
исправлений, документов, других релизов и страниц событий. Счётчик MCP JSON-RPC
не является ключом Telegram-операции.

Скрипт проверяет настоящий протокол, курсоры и доступность исходных фактов.
Он не запускает LLM и не измеряет успешность решения заданий. Оценка 30 задач
и процент успешной первой сборки остаются отдельным выпускным этапом Q1.
