# Bounded streaming webhook dispatch

Status: accepted for R4 memory mode, 2026-11-16. Durable webhook integration and inbound diagnostics remain open.

Bot::webhook is a lazy builder. Startup validates its router/options/listener, verifies the bot identity, binds command mentions and claims the shared SDK source guard. The managed server owns HTTP intake; one supervised dispatcher owns accepted work independently of an HTTP waiter's lifetime. This keeps a disconnected client from freeing queue capacity while its handler still runs. Successful processing, rather than queue admission, permits a 200 response.

A streaming scheduler admits unrelated chats while another chat is active. It retains at most the configured number of active keys, and total queued/active events and canonical payload bytes share finite quotas. Pending and active unknown-scope events are global barriers. Events after a pending barrier cannot bypass it. Each admitted event reuses cancellable SDK dispatch; cancellation aborts and joins admitted handler tasks. Normal/forced shutdown joins the dispatcher before releasing source ownership. External side effects or tasks independently spawned by application handlers remain host responsibilities.

Cache entries hold only update IDs, SHA-256 canonical DTO fingerprints and completion expiry. Object order/whitespace do not distinguish duplicate payloads. Matching in-flight delivery is retryably refused, matching successful delivery is acknowledged, and conflicting content is refused. Unexpired successful entries are never evicted to admit a new key. Failed work is not recorded as success and may be redelivered. This gives process-local deduplication in an explicit window; restart loses it and does not provide exactly-once external effects.

The original ingress deadline is retained across the queue and bounds active work. A failing regression and independent review identified a missing wakeup for expired waiting events while another handler remained busy. A timer for the minimum pending deadline now releases their entry/byte/dedup quotas and barriers before subsequent admission. Three private queue tests cover this boundary, canonical bytes and global barriers; eight HTTP tests cover startup, duplicates, concurrency, disconnects, cache pressure/expiry, handler failures and both shutdown paths. The offline localhost example verifies command routing and one execution for two identical deliveries.
